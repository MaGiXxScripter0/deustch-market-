# Обработка ошибок сохранения заказа

## Цель

Сделать сбой сохранения заказа диагностируемым для команды и понятным для покупателя, не раскрывая внутренние ошибки базы данных в браузере.

## Причина

`POST /api/requests` сворачивает каждую ошибку `place_pickup_order` в один ответ 503. Поэтому известные бизнес-ошибки базы неотличимы от временного технического сбоя. Проверка подключённой базы подтвердила, что оба товара из обращения доступны, а RPC принимает переданные контактные данные, слот и формат позиций до контролируемых отказов.

## Решение

Вынести преобразование ошибок RPC в чистую функцию в `src/lib/request.ts`. Она вернёт только безопасные сообщения и HTTP-статусы: недоступный товар и недостаточный остаток вернут конфликт `409`; неверный слот вернёт `400`; всё остальное останется обобщённым `503`. Route Handler запишет непредвиденную ошибку в серверный лог вместе с кодом Supabase, но не передаст её клиенту.

## Проверка

Добавить unit-тесты чистой функции: известная ошибка остатка даёт 409 и понятное сообщение, неизвестная ошибка остаётся 503 и общим сообщением. Затем выполнить полный набор тестов, линтер и production build.
